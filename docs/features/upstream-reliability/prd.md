## 用户问题

1. 健康 Bash 命令可能被守护机制误杀，工具执行结果不可信。
2. 压缩的多层请求重试可能放大尝试次数，窗口不足或取消时仍进入回退。
3. 后台终态可能与前台确认时序冲突；末尾空 assistant 可能遮蔽有效结果或真实失败。
4. 成员插话在邮箱、历史和 UI 之间缺少稳定关联，重复气泡与等待态难以结算。
5. 团队任务状态、成员活动和消息投递混用，用户无法判断谁在等待什么。
6. 团队配置复用、一次工作授权与动态任务被启动审核绑定，迫使闲置角色制造占位任务。
7. worker、trace、团队档案等资源成本需要测量，而非先认定为卡顿根因。

## 需求与推进等级

### 一级：明确问题或保护缺口

- **REL-001 Bash 生命周期正确。** 正常命令不因 fd 复用误杀，保留 stdin、参数、stdout/stderr、真实退出码；父进程退出、用户取消和后台进程组可以清理；Windows 分支单独说明证据。
- **REL-002 压缩保护。** 一次逻辑压缩共享真实请求尝试预算，包含 fork、fallback、流恢复与上下文过长重试；同一请求只扣一次。取消后不新发请求、不提交成功压缩边界。临界窗口限制输出，宽裕时保持缓存配置，尊重显式输出和思考预算。
- **REL-003 成员插话结算。** 用户直发消息从发送到历史回声有可追溯身份；同文两次发送仍是两条，网络重试不是两条。延迟超过 120 秒、批量投递、重连和恢复仍可结算；他人同文不能吞掉本人的消息。终态、失败和取消能结束对应等待。

### 二级：先验证再决定

- **REL-004 后台终态。** 用前台确认挂起的合成时序验证实时事件、历史和重连。合法终态可靠落盘且可见，旧回合输出继续隔离；重复事件、写入失败、多观察者及 Telegram 投递分别验收。
- **REL-005 空尾结果。** 仅在同一合法请求/响应范围恢复文本；错误、取消、未完成工具不能被旧成功覆盖；不以默认“执行完成”伪装缺失结果。usage 与压缩边界语义保留。
- **REL-006 资源成本。** 用临时库、合成 trace/档案测 worker 退出、替代、取消、锁、读取字节与事件循环；有证据再实施最小改动，不将 RSS 或单次耗时作为全部结论。
- **REL-007 协议与连接。** usage 区分包含/互斥缓存语义；MCP 重连不串项目、scope 或凭据；会话回收保留后台工作、审批和通知。数据不足时记为条件性而非修复通过。

### 三级：需求驱动的协作与能力

- **REL-008 状态与恢复可信。** 复用已包含的 #1426 能力，验证 Stop→新指令→成员原历史续跑、成员退出、主控替换和服务重启。分开任务状态、活动和投递，未知不默认工作中，不重放不确定副作用。
- **REL-009 授权与角色解耦。** 预设保存配置，用户目标限定本次授权；范围内任务不重复确认相同角色配置。已批准角色可以无任务并按需启动；新增成员、权限扩大、隔离或成本边界变化需必要授权。唤醒使用冻结配置。
- **REL-010 交付闭环。** 负责人、产物、验收条件、版本、退回原因明确；同版本无新事实不重复验收；传输回执不一律唤醒模型，有行动要求的消息不得静默。
- **REL-011 可选能力。** 普通子任务并发、精确模型目录、回合结束后换模、文档批注和协议接入，只有场景成立才排实施；批量立即换模、全局 lean、统计分享后置。

## REL-003：成员消息实例绑定（2026-10-27 确认）

**REL-003-M1 缺实例身份即拒绝：** 成员消息 HTTP 请求缺少实例身份时直接拒绝，live/history 零写入；不得按当前同名团队补身份，不自动转投。客户端升级／刷新取得绑定身份后，由用户重新发送。此规则是已确认的接口兼容变化，不表示当前实现已支持，也不扩大到 CLI 或 SendMessage 的其他邮箱入口。

典型场景：旧成员页指向的团队已被删除并同名重建，迟到请求不能投递给新实例；缺身份请求即使带有 messageId，也不能用消息幂等代替实例校验。未升级调用方将发送失败，用户可保留正文，升级／刷新并核对目标后再发送；失败或重试不得自动绑定当前实例。

验收须覆盖缺身份请求及其重试的拒绝、live/history 原内容不变且无新增记录、不补身份或自动转投，以及升级后绑定正确实例的正常发送。完整身份请求在校验与提交之间遇到删除／重建或成员替换时仍须零错投；身份字段、错误协议和提交隔离合同见 [BG-T2](design.md#bg-t2rel-003-成员消息实例边界)，尚须设计验证。兼容政策确认不授权 P2 编码。

## REL-003-C：消费侧实例隔离（2026-10-27 已批准）

团队删除后同名重建或同名成员替换时，旧运行者不得读取、领取、注入或确认新实例消息，包括权限响应与断线队列。合法当前成员仍可正常接收；历史查看不要求启动成员。消费身份只能来自创建、可信注册或有原实例证据的恢复，不得由消费者每轮按当前名字补齐。

无可信原身份的旧记录保持历史只读，不自动恢复消费。原成员仍在名单时可验证后续跑；已移除成员只能由当前合法调用者通过既有显式 SendMessage 恢复入口重新注册，取得新身份并沿用旧历史，不冒称原实例恢复。普通 SendMessage 写信协议、HTTP 缺 session 拒绝、权限政策及 Stop 执行前标记决策不变。

验收覆盖所有自动消费入口、读取与领取之间重建、重复消息 ID／legacy 消息碰撞、队列排空前替换、权限响应、正常 idle／shutdown、旧数据恢复和失败处理。拒绝不仅返回错误，还须保证新实例 live/history 和输入队列不受旧消费者影响。该保证不包括撤回此前合法交付的副作用、exactly-once，亦不保证新成员永远看不到保留邮箱中的旧消息。合同见 Design REL-003-C；证据和状态仅记入 Plan P2-2-C。

## REL-009：团队权限上限（2026-10-27 确认）

用户选择提案 A：**既有团队保留批准时权限上限；扩大需明确增量批准，更严格限制仍生效。** 本节澄清 REL-009 的授权语义，取代“主控改权限即可让既有团队自动跟随扩大”的解释，不代表相关实现已完成。

- **REL-009-A1 批准边界：** 用户批准团队目标和角色时确定权限上限。主控之后扩大权限、预设被修改、服务重启或成员恢复，都不自动扩大既有团队授权；范围内动态任务不因此重复审核。
- **REL-009-A2 增量授权：** 超出原上限的权限只能由用户明确批准，且仅作用于展示并确认的受影响成员和权限差异，不重新审核无关任务与角色。模型消息、继续指令、审批失败或重试本身不是扩大授权。
- **REL-009-A3 更严限制：** 批准上限不是绕过当前更严格限制的许可证；全局禁用、组织限制、OS 权限与预设既有显式限制继续适用。不得新增 Computer Use 逐应用批准。
- **REL-009-A4 旧团队重新确认：** 旧团队缺少可信历史权限上限证据时，允许用户明确重新确认展示的成员和权限后继续原团队，不强制另建团队。确认前不启动、恢复或放行新的模型／工具执行；只读查看已有历史与产物保持可访问，不以启动模型执行“只读任务”代替历史查看。确认建立的是本次明确授权，不是补造历史批准；失败、取消或重试本身不授予权限。已确认权限仍受 A3 的更严限制和既有 Stop 边界约束，授权确认本身不隐含启动或继续。在途工具按 A5 处置。

- **REL-009-A5 在途工具取消：** 限制收紧后不再获准、或旧团队无法证明获准的受影响调用，禁止新的越界执行；对已开始的工具立即请求取消。未确认终止时显示“正在停止／结果待确认”，受影响执行链不得继续，不自动重放。不保证撤回已发生的副作用，也不能把发出取消请求或超时等同于工具已终止；不把仍合法的无关工作一律停止。

典型场景：团队以原权限获批，某角色尚无任务；用户随后只扩大主控权限。角色收到任务时不能自动获得更大权限；只有用户明确批准该角色的增量权限后，才可在仍生效的限制内使用新授权。服务重启不改变这一规则。反向场景是用户收紧限制：已有批准不能用来绕过收紧。

旧团队场景：升级后打开缺少可信历史上限证据的团队，用户仍可查看原会话和交付成果，但读取、刷新和服务重启都不能启动执行。用户明确确认展示的成员及权限后，可在更严限制及合法继续规则内续用原团队；未确认成员不获得该授权，确认失败或取消仍保持执行受限。

验收须覆盖待命与已启动成员、扩大与收紧、审批取消/失败/重试、重启及旧记录，旧团队按 A4 验证确认前后行为。在途工具按 A5 验证取消请求、终止未确认时的状态与执行阻断、不自动重放及副作用披露；具体准入/取消/终止证据协议、模式不可比较时的处理，以及迁移和恢复的技术合同，仍属于 [BG-D1 差异设计](design.md#bg-d1rel-009-批准后权限政策与差异合同) 的待闭合事项；A4 的确认不等于这些合同或实施获批。

## 非目标

- 不整包合并上游，不新增第三套协作系统，不统一重写 Teams 和跨会话协作存储。
- 不因“超时”认定进程死亡，不自动重放可能已发生的 Bash/Edit/外部副作用。
- 不将模型更换、Bun 升级、重试次数增加当通用修复。
- 不承诺 usage 是账单真值，不承诺工具副作用恰好执行一次。
- 不修改既有 Computer Use 全局同意边界，不叠加逐应用授权。
- 不自动发布、提交、推送、替换真实应用或消耗真实模型额度。

## 验收与证据规则

行为测试优先于实现形状断言。每项独立记录失败探针、修复后结果和边界证据，区分 `passed`、`failed`、`skipped`、`blocked`、`not run`。离线通过不能代替真实供应商或安装包结论。新增持久化形状需前向迁移、旧夹具和持久升级门禁。没有复现的风险可保留探针后继续其他批次。

## 许可与数据安全

历史 MIT 修复逐原提交/文件核验，保留声明；后续新许可代码不因摘单文件而变为 MIT。许可未明确不复制代码，可以独立实现已描述的行为要求。研究记录不替代法律意见。测试仅使用临时用户目录、fake key、loopback 和合成数据，不读取真实供应商、历史或团队控制面。
