# IM 消息管道

IM 接入复用 ccmax 的项目会话和 Agent，而不是另一套问答系统。这里说明入站媒体的处理职责、Telegram 本地语音转写的契约，以及读代码时应区分的能力与验证边界。

## 范围与用户行为

当前实现范围是 **Telegram 私聊中的语音便签（`message.voice`）**。已授权用户发送语音后，机器人先提示处理状态，在本机转写，自动交给当前绑定的 Agent，并在 WebSocket 发送成功后回显实际发送的文字。回显不是确认对话框；用户可以继续发文字纠正，已经发送的指令不会因为之后的纠正自动撤销。

- `message.audio` 中的音乐、录音素材，以及作为文档上传的音频，仍是普通文件，不自动替换成转写文本。媒体格式与用户意图是两件事。
- 图片保留既有的内联输入方式；文档、视频保留文件引用方式。
- 微信使用协议中的 `voice_item.text`，接收平台提供的文字，不调用这条本地转写管道。平台没有提供文字时，ccmax 不保证能补转写。
- 本次不迁移 Telegram 的整个聊天运行时，不改变权限卡片和菜单，不增加群聊、混合消息聚合、PDF 解析、云端转写或随应用分发的模型。

本地转写处理的是用户输入。Agent 仍按现有权限模式处理工具调用；语音不会额外授予权限。转写中出现 `/new`、`/allow` 等文字，不会被重新解析为 IM 管理命令。

## 能力边界：引用不等于无法读取

协议层 `AttachmentRef` 仍然只有 `file | image`：

- 图片进入模型的 image block。
- 普通文件通过 `@"路径"` 进入用户消息。Agent 可以在工具与权限允许时读取文本、文档或运行相应工具；这不是直接的多模态输入，也不是“所有文件都无法理解”。
- 音频文件引用本身不会生成转写。转写成功时才有可供 Agent 使用的语音文字。

音频转写失败时保留文件引用，但通知必须明确说明 **语音内容没有识别出来**，请用户改发文字或检查本地依赖，不能仅凭“已转交文件”宣称机器人已听懂。

下载暂存发生在本机。本地 Whisper 不调用第三方转写接口；转写文字、图片和 Agent 读取到的文件内容仍可能发送给该会话所选的模型服务。离线转写不代表整条 Agent 链路离线。

## 模块职责

### 平台入口

`adapters/telegram/index.ts` 负责私聊检查、配对授权、消息去重、会话管理、控制命令和消息回传。媒体下载只能发生在私聊、授权与去重检查通过之后。

`adapters/telegram/inbound.ts` 负责从 Telegram 消息提取惰性下载需求、传递 `voice.duration`、调用共享管道。平台代码知道“这是语音便签”；共享管道不从 MIME 猜测它是不是用户指令。

### 物化与组装

`LocalAttachment` 保留 `kind: 'image' | 'file'`，仅为实际需要的行为增加 `mediaKind?: 'voice'` 和 `durationSeconds?: number`。未标记的附件原样映射为协议附件。

`adapters/common/attachment/pipeline.ts` 消费已物化附件和原始文字，产出：

- 组装后的用户文字；
- 仍需发送的附件引用；
- 用户可见的通知；
- 实际合并的转写文本；
- 取消状态。

这是带可注入转写依赖的异步处理模块，不是数学意义的纯函数。通知输出与平台 SDK 分离，取消和超时属于接口契约。

### 本地转写

`TranscriptionProvider` 的调用输入包括音频字节、MIME、可选文件名与语言、时长上限及 `AbortSignal`。预期失败返回结构化原因；取消必须终止工作并完成资源回收，不能只有一个永远未结束的 Promise。

`whisper-local` 的工作顺序：

1. 查找 whisper.cpp 兼容 CLI、FFmpeg 和用户提供的模型文件；不下载、不安装。
2. 在独立临时目录中写入音频。
3. 使用 FFmpeg 转成 16 kHz、单声道、16 位 PCM WAV。最多解码时长上限加 1 秒，用这一秒判断超长输入；超长输入拒绝转写，不能截断后冒充完整结果。
4. 校验 WAV 的实际数据长度与时长。
5. 调用 whisper.cpp 的 `-otxt -of` 输出契约，读取独立文本文件。stdout/stderr 只作有上限的诊断信息。仅中文语言额外传入 `--prompt` 初始提示；`auto` 与非中文不传。
6. 等待子进程结束，删除本次解码和转写产生的临时目录。

不把 Python `whisper` console script 当成 whisper.cpp。不同 CLI 的参数、模型格式和输出方式不同，“文件可执行”不等于“实现兼容”。语言默认 `zh`；中文不能使用 `.en` 的英语限定模型。中文语言注入默认简体引导 prompt，识别后不再做字典转换。

## 顺序、控制命令与会话归属

普通用户输入按接收顺序进入每个聊天自己的处理队列，先收到的慢语音不能被后收到的文字越过。控制命令与权限回答使用已有的短操作队列，不等待语音完成。

每次入站任务有自己的取消信号和会话归属。会话操作必须遵守：

- `/stop` 取消尚未送入 Agent 的输入，并停止现有生成。
- `/clear`、新建或切换会话使先前待发送的输入失效；转写迟到的结果不能写入清空后的上下文或新会话。
- 同一会话断线恢复不自动改变归属；发送前再次检查会话、授权和连接状态。
- 权限回调、`/answer` 不被本地转写长时间占用队列。
- adapter 关闭时取消待处理工作并回收子进程。`stopTelegramAdapter()` 返回可等待的 Promise；`SIGINT` 和 `SIGTERM` 处理器等待在途转写完成取消与清理后再退出，避免仅触发取消就立即退出而遗留本地进程。

转写的全局并发上限为 2，额外转写等待队列上限为 8；每个聊天最多接收 8 条尚未完成的普通输入，计数从接收而非开始处理时起。超过聊天容量直接拒绝，超过转写容量保留文件降级。待处理消息在授权、去重后入队，下载在聊天队列内执行，尚未开始的任务不持有音频字节。

这些约束不承诺跨进程崩溃后的 exactly-once。WebSocket 写入成功与 Agent 已完成处理是不同的事件；发送失败不自动重试未知结果的操作。

## 文本修正与回显

转写、文本规范化和执行是不同职责：

- 仅中文语言（`zh` 及别名 `zh-CN` / `zh-TW` / `ZH`；空白默认 `zh`）向 whisper.cpp 注入 `--prompt` 初始提示。默认文案为「以下是普通话的简体中文转录。」 `stt.whisperPrompt` 可覆盖，`CC_STT_WHISPER_PROMPT` 环境变量优先；空白环境值回退到文件配置，有效提示词未配置或仅含空白时使用该默认值。`auto` 与非中文不注入。识别后不做简繁字典转换。用户原始手打文字和普通音频文件不处理。共享管道仍去除首尾空白、统一换行。
- 这条 prompt 只是识别引导，不保证输出全部为简体，也不保证纠错。它可以改变数字、标点和用字（例如「请」→「清」）。没有独立的同音字纠错步骤，「戴上」与「带上」仍可能混淆，必须核对实际回显。不额外调用 LLM 或云端服务做润色或纠错。
- 标点首先由识别引擎产出。缺乏证据时不猜测同音字、不自动改写意图。
- 专有名词增强需要针对所选引擎验证热词或提示参数后再引入，当前不宣称已提供。
- 回显必须包含实际发送的文字，以普通文本发送，避免转写内容意外触发 Telegram Markdown/HTML 格式。
- 超过 Telegram 单条长度上限时沿用既有分片工具。

仅有“已转写文件名”的通知不足以让用户发现错误。转写成功也不代表用户指令安全或识别准确；工具操作仍走现有审批。

## 限额与降级

时长上限为 **300 秒**。Telegram 的 `voice.duration` 用于下载前预检，规范化 WAV 的实际时长用于二次检查。压缩字节数不能换算为可靠时长。

转写管道的时间预算默认 **60 秒**。超时触发取消，等待子进程关闭和清理后才释放并发槽；清理可能有短暂宽限期，因此 60 秒不是精确的消息返回时间保证。下载也需要独立的时间和字节边界，不能无限等待或先读完整文件才发现超限。

未配置、引擎/模型/解码器缺失、格式不支持、空结果、损坏音频、超长、超时、输出过大和进程失败均明确降级。空转写不作为成功结果；当前没有独立的语音活动检测，识别引擎仍可能对静音或噪声产生文字，回显与权限检查不能替代真实样本评估。

Telegram 元数据已表明超过 300 秒时，在下载前直接拒绝，因未下载而不宣称文件已转交。其他降级保留已成功下载的文件引用和原有文字，明确说明未识别语音；“已转交文件”只在 WebSocket 发送成功后提示。用户主动取消属于另一种结果：不将音频或迟到文字作为降级消息再发送。

转写用的复制文件、规范化 WAV 和输出文件在完成、失败及取消后清理。下载的原始附件位于 `~/.claude/im-downloads/telegram/`，Telegram 启动时调用 `AttachmentStore.gc()` 清理超过默认 24 小时的旧文件；这是启动触发的清理，不是精确到期删除。长时间持续运行或应用未启动时可能保留更久。从协议附件中省略已转写语音，不等于立即删除原始音频。

## 实施依赖与阶段边界

阶段按可验证的能力递进划分，而不是按文件夹划分。旧版将“平台进模型全链路”放在实际转写器之前，使 Phase 2 的验收依赖 Phase 3；helper 的组装结果也不足以证明入口可用。

| 阶段 | 交付边界 | 必要证据 | 依赖 |
|---|---|---|---|
| Phase 1：最小媒体契约 | 语音便签标记、转写结果、文本组装、降级与取消信号 | 假 provider 的隔离回归；普通图片和文件行为保持兼容 | 无 |
| Phase 2：本地处理可运行 | FFmpeg 规范化、whisper.cpp 文件输出、实际时长、进程回收、显式配置和旧配置兼容 | 假 CLI/解码器的进程测试；配置与写入保留回归；真实解码证据另列 | Phase 1 |
| Phase 3：Telegram 集成 | 实际入口授权与去重、受限队列、命令取消、会话归属、自动投递与纯文本回显 | grammY 入口与本地 WebSocket 集成回归；相关仓库门禁；真实识别与平台冒烟另列 | Phase 1、Phase 2 |

旧编号的 Phase 2（Telegram 接线）与 Phase 3（本地引擎）应分别按现在的 Phase 3 与 Phase 2 重新评估。已有代码可以保留和修复，但阶段完成不能由实现文件存在、helper 通过或历史门禁日志推定。真实识别质量、真实 Telegram 服务和跨操作系统验证始终分别记录，离线集成测试不代表它们已通过。

## 配置与运行环境

默认不开启转写。只有显式配置 `whisper-local` 才调用本地程序。配置优先级为环境变量、`adapters.json`、默认值；配置修改后需要重新启动 adapter。

最低配置是 provider、兼容 CLI、FFmpeg 解码器和多语言模型。设置页暂不提供模型下载或专门的转写面板；配置方法见 [Telegram 接入](../im/telegram.md)。

配置向前兼容由加载边界完成：旧文件缺少 `stt` 时得到关闭转写的默认配置，不要求重写旧文件或增加全局版本标记。桌面设置保存与配对写入应保留 `stt` 整段及其中未知字段；环境覆盖只影响运行时、不覆写用户配置。非法 provider 或字段有明确诊断，不能默默当作已经正常启用。

`stt.whisperPath` / `CC_STT_WHISPER_PATH` 指定识别程序，`stt.ffmpegPath` / `CC_STT_FFMPEG_PATH` 指定解码器，`stt.whisperModel` / `CC_STT_WHISPER_MODEL` 指定模型，`stt.language` / `CC_STT_LANGUAGE` 指定语言，`stt.whisperPrompt` / `CC_STT_WHISPER_PROMPT` 指定中文初始 prompt（空白使用默认引导）。桌面进程的 `PATH` 可能与终端不同，显式可执行文件路径比依赖终端环境更可靠。

子进程使用参数数组，不经 shell 拼接命令；只继承运行所需的环境变量，不继承 Bot Token 或模型服务凭据。测试不得依赖机器上的真实模型、凭据或默认用户目录。

## 扩展和验证边界

新增平台仍需要完成该平台的授权、去重、元数据提取、下载和会话接线；调用一个共享函数不会自动补齐平台协议。已有 `InboundChatMessage` 与 `ImChatRuntime` 不需要另造一套通用消息总线。

未来新增转写 provider 可以复用取消、时长和结构化结果契约；有第二个真实使用场景时再扩展语义类型。当前不引入未使用的五类媒体枚举、处理器注册表或多 provider 自动失败重试。

验证分为三个层次，不能互相替代：

1. 管道与进程契约测试：使用 fake provider、假的兼容 CLI/FFmpeg、临时配置目录，验证文本、时长、取消、资源清理和降级。
2. 入站接线测试：驱动实际 grammY 入口，经过授权、真实本地 WebSocket 和 mock session，验证发送、回显、顺序、取消和恢复。只有 helper 测试不能称为“进模型全链路”。
3. 真实识别验证：使用明确授权的中文 OGG/Opus 样本、指定二进制与模型，记录识别错误和端到端延迟。假程序输出固定中文不证明真实识别质量、静音幻觉率或跨平台兼容性。

macOS、Linux 和 Windows 的解码器安装、执行文件发现与进程终止行为需要分别验证。缺少平台证据时应报告未验证，不能将跳过的测试写成通过。真实识别与真实 Telegram 冒烟需另行授权，不进入离线必需门禁。
